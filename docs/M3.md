# M3 — automation

M1 made Shelv copy files when someone presses a button. M3 makes it copy
them when nobody is watching. That is the whole of the difference, and it
governs the design: every decision here is about what a program may do to
your files while you are asleep.

`docs/PLAN.md` §1.1c–d define the requirement and §5 lists the deliverable.
This records how it is being built and where it departs from the frozen
plan.

## Shipped as six changes

| | | Writes to disk? |
|---|---|---|
| **M3.1** ✅ | When a rule is due — pure evaluation | No |
| **M3.2** ✅ | The tick, the queue, run-on-connect | Starts runs |
| **M3.3** ✅ | The unattended deletion guard | Refuses runs |
| **M3.4** ✅ | Snapshot retention | Yes, deletes |
| **M3.5** ✅ | Tray, run at login, notifications | — |
| **M3.6** ✅ | Next Backup, and the editor | — |

M3.3 lands **before** anything can delete unattended. M3.2 starts runs, and
a mirror run deletes; so the guard is not a later refinement, it is the
condition on which M3.2 is allowed to exist. The order matters more than the
split does.

## The decision the rest follows from

**A schedule says how often, not when.** "Daily" means *the last successful
run was on an earlier local calendar day*. Weekly means an earlier week,
monthly an earlier month. There is no firing time.

This is not a simplification for its own sake. The alternative — "daily at
02:00" — requires a timezone database, a rule for the hour that repeats every
autumn and the hour that does not exist every spring, and persisted
next-run bookkeeping that has to survive the clock being changed underneath
it. All of that to express something a backup does not actually need: a
backup needs to have happened today, not to have happened at 2am.

Three things fall out of it:

- **Catch-up is not a feature.** A machine that was off for a week still
  crossed six day boundaries; when it comes back, the rule is simply due.
  There is nothing to make up, because nothing was missed — only delayed.
- **No timezone database.** The only thing needed from the OS is the UTC
  offset in effect at a given instant, which both platforms answer directly
  and which handles DST by construction, because the OS knows what the
  offset *was*.
- **Run-on-connect stops being a special case.** Plugging a drive in is not
  a separate trigger with its own rules; it is an *opportunity* to notice
  that a rule is already due. The frequency becomes what §1.1d asks for: a
  floor, not an alarm clock.

The cost, stated plainly: a daily rule runs whenever Shelv is next running
on a day it has not yet run, which may be in the middle of your working
afternoon rather than overnight. If that turns out to matter, the fix is an
optional "not before HH:00" that defers a due rule within its period — it
composes with all of this rather than replacing it.

## Four departures from `docs/PLAN.md`

**`catch_up` is removed, as `allow_deletions` was in M1.** §1.1d asks for
catch-up and the schema has a per-rule flag. Under period semantics the flag
cannot change any behaviour: a rule whose period has passed is due, whether
or not it was due earlier. A toggle in the editor that does nothing is worse
than no toggle, so migration 0004 drops the column. What §1.1d actually
wanted — "a missed run executes at the next opportunity rather than being
skipped" — is now unconditional.

The alternative reading, "only run at a boundary observed while Shelv was
running", was rejected: it would mean a laptop that is closed every night
never runs a daily rule at all, which is the failure §1.1d exists to prevent.

**Custom (cron) schedules leave the editor.** They are in the data model and
the editor offers a field for them; nothing evaluates it. Rather than ship a
cron parser inside this milestone or leave a setting that silently never
fires, the option is removed from the editor. A rule that already carries
one — none should, but the column allows it — is shown as an unsupported
schedule, never runs automatically, and can still be run by hand.

**One run at a time, app-wide.** §2.2 describes per-destination-volume locks
so two rules on different drives can run together. The runner already
enforces one at a time, and the queue built here inherits that. Two rules
copying at once compete for the source disk as often as not, so the gain is
unclear and the cost — a lock per volume, and a run that must decide which
of its several destinations it is allowed to start — is real. Left as a
refinement with nothing depending on it.

**A new run result: `refused`.** §2.4's enum is ok / partial / failed /
cancelled. An unattended run stopped by the deletion guard is none of those:
it did not fail, nothing is wrong with the machine, and calling it `failed`
would put it in the column someone checks for broken drives. Migration 0004
adds the spelling.

## What each change has to get right

### M3.1 Due evaluation

`scheduler::due(spec, last_success, now, offset) -> Due | NotDue(reason)`.
Pure: no store, no filesystem, no clock of its own. Everything that decides
whether a backup starts is therefore testable as a table of dates.

- **Local civil dates**, from the Unix instant plus the OS's offset at that
  instant. `engine::stamp` already converts days to a civil date for folder
  names; that arithmetic moves somewhere both can use.
- **A rule that has never succeeded is due**, so a rule created today backs
  up today rather than tomorrow. A rule whose only runs failed is also due —
  the last *successful* run is what the period is measured from, which is
  what stops a broken rule from going quiet.
- **Disabled, manual and unsupported-schedule rules are never due**, each
  with a distinct reason, because the UI has to say which.
- **The source and every destination being unavailable is not "not due"** —
  it is due-but-unreachable. The distinction matters: the first reads as
  "nothing to do", the second as "plug the drive in".

### M3.2 The tick and the queue

- A thread ticking about once a minute, evaluating every enabled rule. A
  minute is far finer than a daily period needs, and it means a rule created
  now starts within a minute rather than at some invisible boundary.
- **Run-on-connect reuses `VolumeWatch`.** It already reports a real change
  in attached volumes once a second and emits only on change. A drive
  appearing makes Shelv re-evaluate; a rule that is due and now reachable
  runs. A rule that is not due does not, however many times the drive is
  replugged — that is the frequency floor doing its job.
- **The queue holds rules, not runs**, deduplicated by rule id, so a rule
  that is due and also just had its drive plugged in is queued once.
- **Manual runs are not queued.** Backup Now already refuses while another
  run is going, and that stays: someone pressing a button gets an answer
  now, not a place in a line whose length they cannot see.
- The trigger is recorded honestly (`schedule` or `on_connect`), because the
  run history is where someone works out why their disk was busy at 14:05.

### M3.3 The deletion guard

The case this exists for: a source folder that mounts empty, or gets
renamed, or is a drive that came back without its data. A mirror faithfully
reproduces that — it removes everything from the backup — and with M1 the
only thing standing between that and someone's photographs was a human
reading the preview.

- **Unattended mirror runs refuse** when the plan would remove more than a
  quarter of what is at the destination, and more than a handful of files.
  Both halves are needed: a percentage alone trips on a five-file folder, a
  count alone never triggers on a large one.
- **Refusing writes nothing at all** — not the copies either. A run that has
  decided the source looks wrong should not half-apply it.
- **Manual runs are unaffected.** The preview is the guard there, and
  someone who has read it and pressed the button has made the decision this
  is standing in for.
- The refusal names what it saw, in the history and in a notification, and
  running by hand shows the same numbers in the preview.

### M3.4 Snapshot retention

- **Only after a run that is `Ok`.** Not partial: a partial run may have
  failed to copy the very file that an old snapshot is the last copy of.
- Only folders Shelv wrote — the name must parse as one of its own
  timestamps — and never the one this run just created.
- `KeepLastN` counts folders; `KeepDays` measures from the folder's own
  timestamp, not its mtime, which a copy tool may have changed.
- **Deleted outright, not moved to trash.** Pruning exists to reclaim space,
  and a trash folder on the same volume reclaims none. This is the one place
  in Shelv that removes data without a way back, so it is the one place that
  is refused unless every condition above holds.
- Mirror rules have no snapshots; their retention setting means nothing, and
  the editor should stop implying otherwise.

**The trash folders are not pruned.** A mirror's `.shelv-trash` still grows
without bound, by decision: it is the recovery path for exactly the mistake
this milestone makes more likely, and an automatic sweep of it would be the
same mistake one month later. The folders are dated; clearing them is
manual, and the About panel or the drives pane should say so.

### M3.5 Tray, login, notifications

- A tray icon, because PLAN §2 requires background operation to be a
  **per-user tray process and never a service** — a service context gets
  `STATUS_CLOUD_FILE_ACCESS_DENIED` instead of OneDrive hydration, so this
  is a correctness requirement before it is a convenience one.
- Closing the window hides to the tray; quitting is explicit. A backup tool
  that stops backing up because someone closed a window is not automated.
- **Pause all**, from the tray and the status bar. The queue keeps
  evaluating but starts nothing, so someone about to travel can stop Shelv
  touching a drive without editing six rules.
- Run at login via `tauri-plugin-autostart`, off by default and offered
  once.
- Notifications on `failed`, `refused` and `partial` only. A notification on
  every success is a notification nobody reads, and the whole value of the
  refusal is that it interrupts.

### M3.6 The UI

- **Next Backup becomes real**: "Due now", "Tomorrow", "When Archive 4TB is
  connected", "Manual only", "Paused". It has shown an em dash since M0
  precisely so it could not lie; the same standard applies now.
- The editor loses Custom schedule and the catch-up toggle, says what
  run-on-connect will do, and stops offering retention on a mirror rule.
- A rule that would be refused by the guard says so in its preview *before*
  the run, since the numbers are already there.

## Verification

- **A table of dates** for M3.1: period boundaries, month ends, leap days,
  and both DST transitions in a southern-hemisphere and a northern-hemisphere
  offset. This is where the milestone is most likely to be quietly wrong, and
  it is pure, so it is cheap to cover properly.
- The queue under a rule that is due, unreachable, then reachable.
- The guard against a source that has been emptied, against a small folder
  where a percentage alone would trip, and — the case that must *not* refuse
  — a legitimate large deletion run by hand.
- Retention against temp directories: the newest never pruned, a
  foreign-named folder never touched, nothing pruned after a partial run.
- On screen under Xvfb for the tray and the Next Backup column.

What this environment still cannot reach: the tray on Windows, run-at-login,
and a real drive being plugged in. The first drive-connect run has to be
tested there, the same way the first backup was.
