# M1 — the backup engine

The first code in Shelv that writes to a disk. Everything before it read,
classified and displayed; this copies files and, in one layout, removes them.
That difference governs how it is built and how it is reviewed.

`docs/PLAN.md` §5 defines the milestone and §5.1 the acceptance criteria.
This records how it is actually being built, including where that departs
from the frozen plan and why.

## Shipped as five changes, not one

The engine is several thousand lines. Reviewed in bulk, a mistake in it is
indistinguishable from the noise around it — and a mistake here loses
someone's files. So it lands in five pieces, each of which leaves the
repository coherent:

| | | Writes to disk? |
|---|---|---|
| **M1.1** ✅ | Planner — walk, exclude, diff | No |
| **M1.2** ✅ | Copier — temp + rename, parallel, cancellable | Yes, creates only |
| **M1.3** ✅ | Mirror deletion into a Shelv trash folder | Yes, moves |
| **M1.4** ✅ | Snapshot layout | Yes, creates only |
| **M1.5** | Backup Now, progress, dry run | — |

Backup Now stays disabled until M1.5. Until then the engine is exercised by
tests alone, which is what "testable without UI" in the roadmap is for.

## Three departures from `docs/PLAN.md`

The plan is frozen, so the divergences are recorded here rather than edited
into it.

**No `tokio` in the engine.** §2.2 sketches one async runtime. Filesystem
work is blocking, and `tokio::fs` is a thread pool wearing an async coat, so
async buys nothing here and costs a runtime dependency in `shelv-core` —
the crate whose whole point is being testable without one. The engine is
synchronous, runs on threads the shell spawns, and reports progress through
a callback trait. The shell turns those callbacks into Tauri events, exactly
as `watcher.rs` already does for volume changes.

**Deletion is not opt-in per rule.** §5.1 requires "deletions never occur
without an explicit per-rule opt-in". The opt-in is now choosing Mirror:
`allow_deletions` was removed in migration 0002 because it asked a question
the layout had already answered. A mirror that will not delete drifts from
its source with every run while appearing to work. The editor states which
behaviour the chosen layout has before the rule is saved.

**Deletions go to a Shelv trash folder, not the Recycle Bin.** §4 T4 says
"delete to Recycle Bin where available". On removable drives it frequently
is not: Windows often has the per-volume recycle bin disabled there, and
`IFileOperation` then deletes permanently — the precise outcome the recycle
bin was chosen to prevent. Backup destinations are overwhelmingly removable
drives. Moving to `<destination>/.shelv-trash/<timestamp>/` instead is on
the same volume, so it is a rename rather than a copy; it works on every
filesystem; and it can be tested here rather than taken on trust.

## What each change has to get right

### M1.1 Planner

Walks the source, applies excludes, stats the destination, and produces a
plan. Nothing else. It is the only phase that can be built and reviewed with
no possibility of data loss, so the guards belong here.

- **Escape containment (T2).** Canonicalise both ends; reject any resolved
  path that is not a descendant of the rule root. `symlink_metadata`, and do
  not follow links by default — a link inside the source tree is otherwise
  a way to redirect the copy outside it.
- **Depth cap and cycle detection**, for the same reason.
- **Diff** on size and mtime, compared within `VolumeInfo::mtime_tolerance`
  — FAT32 stores mtimes to two seconds, so an exact comparison against an
  NTFS source marks every file changed and re-copies the whole tree forever.
- **Case folding** through `CaseSensitivity::fold` when indexing the source,
  or on a case-insensitive volume two names differing only in case collide
  and mirror deletes one of them as extraneous.
- **Excludes** via `globset`.

### M1.2 Copier

- **Temp file plus rename**, always. This is the whole of the first
  acceptance criterion: pulling the drive mid-copy must never leave a
  truncated file where a good one was. The temp file lives on the
  destination volume so the rename is atomic.
- **Long paths** through `PlatformFs::long_path`; a Lightroom tree exceeds
  260 characters routinely.
- **Bounded parallelism**, low. Oversubscribing a mechanical external drive
  makes it slower, not faster.
- **Partial, not OK**, whenever any file could not be read or written. A
  backup tool that cannot tell those apart is worse than none.
- **Cancellation** checked between files; temp + rename means a cancelled
  run leaves nothing behind.

### M1.3 Mirror deletion

- Moves into `<destination>/.shelv-trash/<timestamp>/`, keeping the relative
  path, so recovering a mistake is a matter of moving it back.
- The trash folder is excluded from the walk, or the mirror starts
  reflecting its own deletions.
- Counted into `RunStats::files_deleted` and previewable before the run.

### M1.4 Snapshot

A new timestamped folder per run, and nothing already written is ever
touched. No diff and no deletion — it reuses the copier and skips the
planner's destination side. Retention stays in M3, so snapshots accumulate;
the editor already says pruning is governed by the retention setting, which
must not imply it is happening yet.

### M1.5 The app

Backup Now becomes real. A run on a background thread, progress throttled to
about ten events a second so a million-file run does not flood the IPC
channel, cancellation, and the outcome landing in Last Result and Last
Backup. A Mirror rule that would delete shows its plan first, satisfying
"previewable before the first destructive run". Zip packaging is M4, so a
rule configured for it is refused with a message that says so rather than
silently copying plain files.

## Verification

Per phase, and all of it runnable on Linux:

- The planner and copier against temp directories: a file that changed by
  size, one that changed by mtime alone, one identical, one excluded, a
  symlink pointing outside the tree, a cycle, a name differing only in case.
- **Interruption** specifically: kill a copy mid-write and assert the
  destination still holds the previous complete file and no temp file
  survives. This is the acceptance criterion most likely to be quietly
  broken by a later refactor, so it gets a test rather than a promise.
- Deletion into the trash folder, and that a second run does not mirror the
  trash folder itself.
- On screen under Xvfb for M1.5, against real directories, with the run
  history and progress checked.

The two things this environment cannot test remain the Windows specifics:
long-path behaviour past 260 characters, and mtime granularity on a real
FAT32 or exFAT volume. Both are called out where they are relied on.
